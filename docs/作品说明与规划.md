## 二、作品正文（项目介绍草稿）

**一句话**  
面向法律软件与合规相关研发的**离线最小能力集**：在**不依赖运行时云端大模型与业务数据上公网**的前提下，完成**案号格式校验**、**民事判决书单条结构化抽取**（固定管线 `civil-judgment-v1`）与**本地合规规则扫描**，输出可追溯的规则引用与结构化 JSON，便于竞赛评审、内训与集成调试。

**要解决什么问题**  
法务/合规类系统在开发与联调阶段，往往需要反复校验案号形态、从裁判文书中稳定抽取关键字段、并对粘贴的文本或代码片段做**确定性**的敏感模式提示。本作品将这三类高频动作收敛为**同一套 HTTP API + Web 控制台**，降低「临时脚本 + 口径不一致」带来的返工。

**核心能力（与界面 Tab 一致）**

1. **案号校验**：对候选案号做规则校验，返回是否合格、归一化信息与规则 ID（如 `CN-YEAR-SP-001`），非法场景附带原因码与可读说明。
2. **文书抽取**：走**冻结的一条**民事判决书管线；成功则返回法院片段、案号、案由、裁判日期等结构化字段；与管线或标记不匹配时返回明确错误码（如 `PIPELINE_MISMATCH`），**不以「猜类型」掩盖契约失败**。
3. **合规扫描**：基于本地规则集对输入文本扫描，输出命中列表（含 `ruleId` 与严重级别如 deterministic / suspicious），支持零命中与仅可疑级等演示路径。

**产品与工程亮点**

- **契约先行**：OpenAPI 描述请求/响应与错误语义，前后端与验收对齐（见 [contracts/openapi.yaml](../contracts/openapi.yaml)）。
- **黄金样例回归**：合成 fixture 与场景矩阵，便于答辩与 `mvn test` 回归（见 [golden-fixtures.md](./golden-fixtures.md)）。
- **非功能口径一致**：单次处理预算与超时语义（含 504、文书路径 422 等）在文档与实现中统一（见 [README.md](../README.md) 超时映射、[api/nfr-and-timeout.md](./api/nfr-and-timeout.md)）。
- **技术栈**：后端 Spring Boot 3（Java 17+），前端 Vue 3 + Vite + Element Plus。

**适用场景**  
竞赛演示、课程大作业、法务/合规工具链的原型验证，以及需要**可解释、可回归**规则能力的研发辅助。

**数据处理与安全叙事（对外必守）**

- 仓库内示例均为**合成演示数据**；公开演示**请勿**使用真实当事人或可识别案情。
- 建议在本机或内网运行；核心三功能**不得要求**将粘贴内容上传到公网服务才能完成（与 [README.md](../README.md) 一致）。
- 本 MVP **刻意不包含**：登录与账号体系、运行时依赖 API Key 的云端大模型作为核心业务路径、审计日志产品化；**不得在对外材料中虚假宣传**上述能力。
- 系统输出为研发辅助与规则命中提示，**不替代**律师、司法机关或本单位合规/安全负责人的专业判断；未经基线或固定任务集的量化提效比例不作为本版承诺（见 [mvp-acceptance.md](./mvp-acceptance.md) 答辩金句）。

## 三、操作说明

### 3.1 环境要求

与仓库 `backend/pom.xml`、`frontend/package.json` 对齐：

| 组件 | 要求 |
|------|------|
| JDK | **17+**（POM 指定 17；可用 21 等更高 LTS 运行） |
| Maven | 建议 **3.8+** |
| Node.js + npm | 建议使用**当前 Node LTS**（README 验收机示例：Node 22 / npm 11） |

**首次克隆**：在 `frontend/` 目录执行 `npm install` 后再启动前端。

### 3.2 启动应用

1. **后端**（默认 `http://localhost:8080`）

   ```bash
   cd backend
   mvn spring-boot:run
   ```

2. **前端**（默认 `http://localhost:5173`，`/api` 代理到 8080）

   ```bash
   cd frontend
   npm install
   npm run dev
   ```

3. 浏览器打开 **`http://localhost:5173`**。界面为三个 Tab：**案号校验**、**文书抽取**、**合规扫描**。

### 3.3 界面演示路径（概要）

完整逐步案例（含期望结果与 fixture 路径）见 **[USAGE.md](./USAGE.md)**，推荐按该文档走通以下节奏：

| 顺序 | Tab | 要点 |
|------|-----|------|
| A | 案号校验 | 合法案号示例 → 合格 + 规则引用 |
| B | 案号校验 | 缺年号非法示例 → 不合格 + `reasonCode` |
| C | 文书抽取 | `success-sample.txt` 全文 → 成功 + `extract` 字段 |
| D | 文书抽取 | `pipeline-mismatch-sample.txt` → 失败 HTTP 422 + `PIPELINE_MISMATCH` |
| E–G | 合规扫描 | deterministic 命中 / 零命中 / 仅 suspicious（见 USAGE 案例 E–G） |

案号、文书、合规的 **curl** 示例与 PowerShell 注意点（如使用 `curl.exe`）同样写在 [USAGE.md](./USAGE.md) 与 [README.md](../README.md)。

### 3.4 回归测试

```bash
cd backend
mvn test
```

## 四、产品规划

以下规划在**不违背当前契约冻结与 MVP 不做清单**的前提下描述演进方向；实施前须按 [mvp-acceptance.md](./mvp-acceptance.md) 协作约定评估对 Scenario 与 fixture 的影响。

### 4.1 近期（巩固 MVP）

- **规则与标准库**：在 `synthetic-demo` 标注策略下，扩充案号边界用例与合规规则 ID，保持「每条规则可追溯至 fixture」。
- **可观测性（研发侧）**：结构化日志、基础指标（请求量、422/504 比例）；**不**等同于产品化「审计追踪」（当前范围仍不承诺谁在何时处理了哪条业务数据）。
- **文档与演示**：维护 USAGE 与答辩材料同步；若对外需要英文版 README/一页纸，单独增补不改契约真源。

### 4.2 中期（能力扩展，仍优先离线/可解释）

- **文书管线**：在 OpenAPI 与 golden-fixtures **显式版本化**后，**审慎**增加第二条冻结管线（例如裁定书、调解书），每条管线独立 `pipelineId` + `schemaVersion`，失败语义保持「契约失败而非模型猜测」。
- **合规规则集**：分级策略、规则包切换（如「演示包 / 内训包」）、导出命中报告（JSON/Markdown）。
- **部署形态**：Docker Compose 一键起停；可选仅 API 模式供 CI 与其他服务调用。

### 4.3 长期（与 xq 愿景区分后的可选方向）

长期愿景见 [xq.md](./xq.md)；与当前 MVP 冲突时以 [buchong.md](./buchong.md)、[mvp-acceptance.md](./mvp-acceptance.md) 为准。可选方向包括（均需单独立项与合规评审）：

- **账号与租户**：多用户、RBAC、API Key（仅当明确脱离「匿名本机演示」定位时）。
- **可选外接能力**：知识库、NL→代码等**不得**静默替换当前三条核心路径的离线契约；若引入大模型，须在架构上隔离为**可选插件**并标明数据出境与留痕责任。
- **效果度量**：任何「提效 X%」类表述须绑定基线任务集与打分表后再对外宣传。

### 4.4 明确不在本规划内默认承诺的事项

与 README / mvp-acceptance 对齐：**全国案号全集司法认证**、替代专业法律意见、未经验证的量化业务收益、运行时强制依赖公网 LLM 完成案号/文书/合规核心链路。
