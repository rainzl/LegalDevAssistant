# 参赛版需求补充与设计协作说明

本文档对齐主需求 [`xq.md`](./xq.md)，并固化 **MVP 边界、合规前提、离线规则版定位**（与主线「大模型底座」如有冲突，以本补充为准：本版**运行时不调用需 API Key 的云端大模型**）。

---

## 一、补缺项（相对主需求文档）

| 补缺项 | 为什么重要 |
|--------|------------|
| **MVP 边界** | 只做「案号校验 + 1 条文书抽取 + 合规扫描」三件套，其余标为后续。 |
| **用户与权限** | 无需登录、匿名试用；**没有 API Key、没有审计日志**（产品侧不设计此类能力）。 |
| **数据与合规** | 演示数据必须合成/脱敏；说明「不向公网外流哪些数据」；**去掉运行时的云端大模型调用**（本仓库交付为本地/内网、规则 + 标准库驱动）。 |
| **标准库来源** | 案由、法院、文书类型等：**公开标准 + 自维护 JSON/YAML**，写清版本号与更新人，避免被认为「随意编造枚举」。 |
| **技术栈明细** | Java 版本、**Spring Boot**、**Vue3 + 构建工具（如 Vite）** + Element Plus。 |
| **非功能指标** | 并发约 **20**；单次处理超时 **10s**；**离线仅用本地规则与本地标准库**校验。 |
| **效果度量** | 「效率提升 40%」等需对应**基线**：同等任务人均小时数或**固定任务集打分表**。 |
| **免责与正确使用说明** | 法律逻辑、法条引用**不得宣称替代专业判断**；生成内容仅供参考，须经人工与测试；利于答辩与观感。 |

**与 `xq.md` 的衔接说明**：创新点中的「垂直领域、合规内置、兼容 Cursor、知识沉淀」仍成立；其中「智能」在本 MVP 中体现为 **领域规则 + 标准库 + 模板化输出**；团队可用 Cursor **在开发阶段**辅助写代码，**不作为**产品运行时依赖。

---

## 二、配合方式（核心原则）

1. **真源在标准库与规则，不靠「模型口头真」**  
   枚举与规则以 **公开标准 + 仓库内 YAML/JSON（带 version / maintainer）** 为准；生成与校验须能对应到**库内条目或规则 ID**，禁止虚构官方枚举。

2. **MVP 三件套锁死**  
   仅：**案号校验**、**一条固定文书抽取管线**（输入/输出 schema 固定）、**合规扫描（规则为主）**；其余一律「后续」。

3. **无账号、无密钥、无审计前提下的安全表达**  
   不向公网发送业务数据（README/答辩需写明）；合规检测依赖**本地模式与规则**；若未来接云端模型，单列版本，**不纳入本 MVP 承诺**。

4. **演示数据红线**  
   只用合成/脱敏样例；对用户粘贴内容提示风险；可做长度与本地处理说明。

5. **与非功能对齐**  
   按「约 **20** 并发、**10s** 超时、离线仅本地规则」做设计与验收；超时**降级**（明确错误或部分结果），不以「慢一点」糊弄。

6. **效果与免责可追溯**  
   量化话术须配任务集与基线；对外免责声明统一口径。

7. **多窗口协作**  
   每个 Cursor 对话尽量**单角色**；契约与黄金用例为**单向工件**：其它窗口引用，勿静默改语义。

## 三、清晰可执行的实现步骤

| 步骤 | 内容 | 对应补充 |
|------|------|-----------|
| 1 | **冻结 MVP** 与用户可见范围（三件套）；README 写明无登录、无 API Key、无审计、无外发。 | MVP / 合规 |
| 2 | **标准库 v0.1**：仓库内结构化文件 + `VERSION` / `MAINTAINER` / 出处；非法定全覆盖处标 **synthetic**。 | 标准库来源 |
| 3 | **Spring Boot 后端**：Java 版本写进构建描述；加载标准库；**10s** 超时；并发策略贴合 ~20。 | 技术栈 / 非功能 |
| 4 | **Vue3（Vite）+ Element Plus 前端**：三功能对应路由或分区；匿名访问。 | 技术栈 |
| 5 | **文书抽取**：仅一条管线——固定文书类型或字段集、固定输出 JSON Schema；不写「任意文书 AI 猜」。 | MVP |
| 6 | **合规扫描**：正则/关键词 + 可选轻量结构化扫描；分级输出（确定/可疑/建议）。 | 离线 / 无外发 |
| 7 | **复制导出**：一键复制代码块与简短「给编辑器用的说明」，**不要求**运行时调 Cursor/Claude API。 | 工作流嵌入 |
| 8 | **黄金用例**：20～50+ 条 fixture，覆盖案号边界与合规负例；可脚本回归。 | 质量与答辩 |
| 9 | **答辩一页纸** 与 **推广使用说明** 落盘：**[`docs/defense-one-pager.md`](./defense-one-pager.md)**（数据流、非公网、免责、NFR、演示三步口播）；**[`docs/USAGE.md`](./USAGE.md)**（环境与 Web/API 全流程案例）。 | 免责 / 效果度量 / 推广 |

## 四、多对话窗口分工 + Cursor 对话模式说明

### 4.1 Cursor 模式速查（与官方能力对应）

| 模式 | 适用场景 |
|------|----------|
| **Plan** | 先对齐方案与取舍（读多写少），适合范围、架构、契约**形态讨论**，再决定是否改仓库。 |
| **Agent** | 在仓库内**具体实现**：改代码、 YAML、OpenAPI、测试、脚本等。 |
| **Debug** | 已有失败现象（构建失败、测试红、运行时错），**按证据追溯根因**并修复。 |
| **Multitask** | 把一个目标拆成**多个并行后台 Agent**，适合前后端、多模块**同时推进**且不抢同一文件的冲突场景。 |
| **Ask** | **只读**问答与核对（不改仓库），适合做口径确认、答辩预演、读代码解惑。 |

### 4.2 窗口与「主对话模式」

**主模式**为该窗口日常打开对话时的首选；括号内为**允许的临时切换**。

| 窗口 | 职责简述 | **主对话模式** | 说明 |
|------|----------|----------------|------|
| **A** 需求 / 产品 | MVP、验收标准、演示脚本、「不做清单」 | **Plan** | 需要改 `docs/` 里成稿时可短期切 **Agent**；只做口头评审时用 **Ask**。 |
| **B** 架构 / 技术 | 分层、模块、非功能、部署与排除项检查 | **Plan** | 定稿后要落 `_架构说明_.md` 等可切 **Agent**。 |
| **C** 领域 / 标准库 | YAML/JSON 真源、版本与出处字段 | **Agent** | 核对条文是否可查而不改文件时可用 **Ask**。 |
| **D** 接口 / 契约 | OpenAPI 或等价约定、请求响应示例 | **Plan** ↔ **Agent** | **从零讨论接口**：先用 **Plan** 定字段与错误语义；**定稿写入仓库**（如 `contracts/openapi.yaml`）用 **Agent**。若你已想好接口只缺落盘，可全程 **Agent** 并严格限定修改范围。 |
| **E** 规则 / 模板与用例 | 规则 ID、fixture、覆盖清单 | **Agent** | 仅讨论用例矩阵不改文件时用 **Ask**；大规模生成用例可配合 **Multitask** 拆文件。 |
| **F** 开发实现 | Spring Boot + Vue 按契约实现 | **Agent** | 疑难杂症切 **Debug**；与 E 并行补测试时可开 **Multitask**。 |
| **G** 测试 / Review | 自动化测试、静态与安全关注点、卡点回归 | **Agent**（**Debug**） | **主：**写测试、跑脚本；**红字排错：**切 **Debug**；只做 Code Review 不动手时用 **Ask**。 |

**Multitask 使用建议**：当 **F** 与 **E** 或其他 **Agent** 需同时推进、且工件冲突可控时，在 **Agent** 或 **Plan** 中发起并行子任务时使用 **Multitask**（例如「后端实现」与「前端页面」各占一条后台 Agent）。

## 七、开工任务顺序（环境、脚手架、Figma）

*本节固化协作对话 ID **`5486cc0e-ae5d-4bee-9047-65c5f68d7cdc`** 中约定的**角色先后、布置任务顺序、前后端环境与 Figma 落页时机**。（本地若无同名 transcript 备份，仍以本节条文为准执行。）*

### 7.1 谁先开工？

### 7.2 分阶段布置任务（推荐）

1. **A（Plan）**：验收标准、「不做清单」、演示脚本要点。

产出：**一页冻结结论** — 详尽条文以 [`mvp-acceptance.md`](./mvp-acceptance.md) **「阶段 0 冻结」** 为真源；[`README.md`](../README.md) 与本文只做摘要与链接对齐。

#### 阶段 1 — 契约与标准库（宜早于或可微调并行于脚手架，但契约宜尽早）

3. **D（Plan → Agent）**：`contracts/`、`docs/api/` 等 **OpenAPI / 示例**。

验收：**后端可编译**、`npm install` + `npm run dev` **跑通占位页**，再绑业务接口与页面。

#### 阶段 3 — 核心业务与功能页

7. **F（Agent）**：按 **D** 实现 MVP 三个 API；接入 **C** 的标准库与规则 ID。  
8. **F（Agent）**：三功能分区或路由（对齐契约三项能力）。

#### 阶段 4 — 根据 Figma 生成 / 对齐页面

### 7.3 并行（可选）

- **Multitask**：例如「后端 Controller + Service」与「前端 `client.js` + 某一屏 UI」分两路 Agent，**前提**为契约已冻结、避免争抢同一契约文件。**具体操作与可复制 Prompt 见下文第八节《窗口 F：阶段 2 Prompt 与 Multitask 分步操作》。**  
- **Figma 视觉**与**后端规则**可同时推进，仍以 **契约 + MVP 三线**对齐。

### 7.4 一句话流程（背诵版）

```text
A(Plan 冻结) → B(Plan 架构/版本)
  → D(契约) + C(标准库)
  → F(安装环境 + 脚手架)
  → F(接线 API + 三功能占位)
  → F(按需：Figma → Vue 精细化)
  → E(固件/用例) → G(测试/Debug)
```

### 7.5 与第六节的关系

- **第六节**：偏「接力」谁在前谁在后（含 E、B 顺序）。  
- **本节**：偏「从零到可演示」的**落地流水线**，含 **JDK/Node、脚手架、Figma**；二者可同时遵守：**先做 A/B 决策 → 契约与库 → 环境与代码 → Figma → 测试收口**。

## 八、窗口 F：阶段 2 Prompt 与 Multitask 分步操作

本节把 **§7.2 阶段 2**（环境与脚手架验收）及 **并行改前端 / 后端** 时可直接粘贴的 Prompt 固化为仓库真源；并说明「两路 Agent」在 Cursor 里**怎么点、怎么做**。

### 8.1 前置条件（必看）

| 检查项 | 说明 |
|--------|------|
| 契约冻结 | Multitask 或双对话并行时，**不要**修改 `contracts/openapi.yaml`、`docs/api/**`（除非已停并行、走窗口 D）。 |
| 目录隔离 | **后端轨**只动 `backend/**`；**前端轨**只动 `frontend/**`。 |
| 仓库根 | 在 Cursor 中打开 **本仓库根目录**（含 `backend/`、`frontend/`、`docs/`）。 |

### 8.2 F — 主 Prompt（阶段 2 验收 / 新机跑通）

**模式：`Agent`**。将以下整段作为**新对话第一条**发送（可用 `@` 引用 `docs/buchong.md`、`README.md`、`docs/_架构说明_.md`）。

```text
你是窗口 F「开发执行」——执行 buchong §7.2「阶段 2：环境与脚手架」在当前仓库的落地验收。

必读：@docs/buchong.md、@README.md、@docs/_架构说明_.md。契约已冻结，禁止修改 @contracts/openapi.yaml 与 @docs/api/**。

目标：确认本仓库已满足「后端可编译、前端可安装运行、与 README 端口/代理一致」，不足处**最小补丁**只写在 README 或工具配置，不改 MVP 业务语义。

请依次做并简要报告结果：
1）环境：Java 17+、Maven、Node/npm 是否满足 backend/pom.xml 与 frontend/package.json；
2）`cd backend && mvn -q test`；
3）启动后端 `mvn spring-boot:run` 与前端 `cd frontend && npm install && npm run dev`，确认 5173→8080 代理与三接口路径与 @contracts/openapi.yaml 一致；
4）若 README 缺「Windows / 换端口 / 首次构建」等，只增补开发说明段，不写 marketing。

禁止：引入登录、云端 LLM SDK、改 openapi。完成后列出「阶段 2 结论：通过 / 缺口项」。
```

### 8.3 「两路 Agent」怎么做：分步说明

很多人困惑的点是：**Multitask 不是魔法**，本质是**两件不抢同一文件的开发任务同时进行**。下面给出两种做法，**推荐先会方式一**。

#### 方式一：双对话窗口（最推荐，步骤最少）

这样做的效果与「并行两路 Agent」相同，且你能**同时看到两个聊天的输出**，最容易排查问题。

1. **准备**  
   - 确认：近期**不会**有人去改 `contracts/openapi.yaml`（契约已冻结）。  
   - 在 Cursor 里已经打开本仓库根目录。

2. **开第一个 Agent 对话**  
   - 打开 **Agent**（或 Composer）新会话，建议在会话标题或第一条自行备注：`F-后端轨`。  
   - **整条复制**下文 **§8.4.1**「后端轨 Prompt」代码块内的文字，粘贴发送。

3. **开第二个 Agent 对话（不要关掉第一个）**  
   - 再开一个 **新的** Agent 会话，备注：`F-frontend轨`。  
   - **整条复制**下文 **§8.4.2**「前端轨 Prompt」代码块内的文字，粘贴发送。

4. **等待两边都做完**  
   - 两个会话会各自改不同目录：`backend/**` 与 `frontend/**`，一般不会 Git 冲突。

5. **你自己做合并验收（必须手动做一次）**  
   - 终端：`cd backend && mvn test`  
   - 终端：`cd frontend && npm install && npm run build`（若项目里有 build 脚本）  
   - 浏览器：`npm run dev` + 后端已启动，点一圈 **案号 / 文书抽取 / 合规** 三区域。

6. **若只有一个会话报错**  
   - 失败的那条路单独 **Debug** 模式打开同目录继续修；**不要**让另一条路同时改同一文件救火。

#### 方式二：Cursor Multitask（单入口、后台并行）

若你的 Cursor 版本在 Chat / Agent 界面提供 **Multitask / 多任务 / Run agents in background** 一类开关：

1. **打开 Multitask**  
   - 按产品当前 UI：在对话界面启用「多任务」或「后台并行 Agent」（名称以你安装的 Cursor 版本为准）。

2. **先发「总控」说明（可选但有用）**  
   - 第一条简短写：`请在后台拆成两个互不重叠的任务：任务 A 只改 backend，任务 B 只改 frontend；禁止修改 contracts。任务 A/B 的正文分别如下——`  
   - 紧接着分两粘贴 **8.4.1** 全文与 **8.4.2** 全文（或分两条消息发送，以你界面是否支持为准）。

3. **等待后台通知**  
   - Multitask 跑完后界面通常会提示「某 Agent 已完成」；再到仓库里 `git diff` 或直接跑 **8.3 方式一第 5 步** 的验收命令。

4. **若界面里没有 Multitask**  
   - **直接使用方式一**，不必纠结开关名称。

### 8.4 F Multitask — 两段专用 Prompt

#### 8.4.1 F Multitask · 后端轨 Prompt

```text
[F-Multitask · 后端轨] 你是窗口 F。契约冻结：不要打开或修改 contracts/、docs/api/。

仅修改 backend/**：可做 pom/资源/application 注释/与超时线程池相关的小调整，使 `mvn test` 稳定，并与 README、`docs/_架构说明_.md` 所述的 10s、约 20 并发口径一致。不要改 API 路径、JSON 字段名、HTTP 状态码语义。

范围外：frontend/** 只读不改。

结束条件：`cd backend && mvn test` 全绿；回复列出改动的文件路径列表。
```

#### 8.4.2 F Multitask · 前端轨 Prompt（含 Figma）

```text
[F-Multitask · 前端轨] 你是窗口 F。契约冻结：不要修改 contracts/openapi.yaml；API 仍通过 src/api/client.js 访问 /api，请求体字段与现有调用保持一致（含 pipelineId、schemaVersion 等）。

仅修改 frontend/**：
1）用 Vue 3 + Vite + Element Plus 优化版式与信息架构；若有设计稿，对齐以下 Figma Make 原型（无法自动读节点时，用截图或手工对照色/间距/层级，功能不减）：
   https://www.figma.com/make/mIuaQeuregICSucen00IqR/%E6%B3%95%E5%BE%8B%E9%A2%86%E5%9F%9F-AI-%E5%8A%A9%E6%89%8B%E5%8E%9F%E5%9E%8B?t=9s4EU5uo1ZYMWVb1-6
2）保持 MVP 三功能（案号校验、文书抽取、合规扫描）分区清晰；不新增依赖后端新接口的能力。
3）`npm run build` 无报错（若仓库无 build 脚本则至少 `npm run dev` 可启动）。

范围外：backend/** 只读不改。
```

### 8.6 沟通与冲突处理（简表）

| 情况 | 做法 |
|------|------|
| 想同时动后端配置和前端样式 | 用 **8.3 方式一** 或 **8.3 方式二**，并遵守 **8.1 目录隔离**。 |
| 必须改接口路径 | **先停止**两路并行 → 窗口 **D** 改契约 → 再窗口 **F** 单线改前后端对齐。 |
| 两路改了同一文件（罕见） | `git diff` 看冲突；开**一个** Agent 会话专门做合并，并再跑 `mvn test` + 前端 build。 |
